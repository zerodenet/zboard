# P4：独立计量报告身份

`0063` 新增 `metering_report_receipts`，按原来的 `(node_id, report_id)` 保存对应协议端点、原账务行 ID 和登记时间。它属于权威恢复状态；诊断正文和图表读取各自保留原职责。原始字节、计费字节、倍率、逐报告舍入证明、累计游标及额度算法均保持原路径。

三个现有计量写入入口都通过同一个账务后置边界，在额度、TrafficRecord 和统计恢复意图的原事务中提交收据。写入收据失败使整个尚未确认的计量事务回滚。新增事实遇到已有报告身份冲突时返回错误，事务内已写的额度、明细和投影意图一起回滚。不会对一个新事实静默忽略冲突。

原生批量处理的已知报告去重和合并窗口碰撞检查优先读取这张窄表。已知收据重放可在历史明细暂时不可读时返回原端点身份，避免依赖诊断或账务明细加载。MySQL 继续由数据库判断大小写、重音和填充等价，合并窗口的原回退保护仍保留。

升级后的旧报告按需要兼容：每次最多 200 个待查身份，使用原 node/report 唯一索引，只读取原账务行 ID、节点、报告 ID 和端点，在同一事务登记收据。登记时间表示这次收据建立时间，不代表节点采集时间、新鲜度或配置交付确认。启动时不扫描或回填全部历史数据。

正式迁移和恢复路径均核对列、非空约束、复合主键和源报告列的实际排序规则；新表继承旧列的身份等价规则。记录已存在而表或身份字段丢失时停止启动和复制，要求先恢复证据。只有无收据数据的原有空业务表恢复路径可先恢复基础表，完成准备后再次验证。迁移复制包含收据，旧版来源缺少这张新表时保留索引兼容读取。

本批给原来每个账务报告增加一个窄收据，短期数据库写入和空间会增加。32 流 SQLite 批次的原 37 次写入、99 个逻辑影响行约束继续检查，另精确检查一次 32 行收据插入；最终成本以专项基准及完整容量实测为准。

验收覆盖真实 SQLite/MySQL：收据 SQL 写入失败整批回滚；报告重放被禁止读取 TrafficRecord 时仍不重复计费；MySQL 重音/大小写身份保持；旧事实兼容读取不加载 Meta；重复迁移、已记录缺表/缺列拒绝及显式恢复、账务与收据复制。原账务、nonce 和舍入证明逐项保留。明细不可读故障使用查询拦截，测试和生产都没有据此删除账务历史。

这仍是完整保留策略的前置。收据数量随报告增长；尚未完成全库总增长上限或有限回放窗口。历史覆盖未完成时仍有受限索引兼容读取。累计游标、独立对账、统计重建、其他历史读取者、旧二进制写入及归档恢复链路全部核对前，不允许生产归档或删除 TrafficRecord，也不删除收据或 FlowUsage。旧二进制不会写新收据；回退时继续保留原始账务事实，并停止新二进制 worker 后按原规则恢复未决任务。

默认单进程和可选投影 worker 都继续使用同一数据库模型；worker 不负责记账或自行补造报告身份。无内核、Connector 或外部支付插件改动。

## 同批次等价身份修复及尚未通过的验收
