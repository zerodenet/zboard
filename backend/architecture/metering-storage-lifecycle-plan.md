# 流量存储与淘汰重构方案

日期：2026-11-12。状态：已进入实现；当前实现、验收与未启用边界见 [实施说明](metering-storage-lifecycle.md)。未构建、部署或清理生产数据。

## 1. 目标与已有边界

目标是“原始报告处理后合并保留结果”，使长期存储主要随业务主体、结算周期与必要统计维度增长，
而不是随每次上报、每条连接和每次回收动作增长。保留无限期合法历史补报、原有扣量和重置语义。
普通关闭、协议删除、用户删除和终止资产的既有准入规则不在本方案中放宽。

规模设计参考为1000万条/小时，约2778条/秒、2.4亿条/天；仅用于检查数据表示和增长方向，
按用户最新要求，不作为本轮压测或验收指标，也不是现有sg-server承载结论。
“1000万条报告”和“1000万个不同计费主体/连接”必须分开验收：重复维度可聚合，真实不同业务信息不能凭空消失。
不承诺任意规模、任意乱序输入下都能固定在64MiB或每份完整记录几个字节。

## 2. 核心处理顺序

```text
接收有稳定身份的报告
  → 可恢复暂存（未确认入账前不可丢）
  → 身份去重 / 检查重复和冲突
  → 按原累计floor求增量
  → 按原权益、倍率、限额、顺序逐样本计算扣量
  → 同批同计费维度合并
  → 一个数据库事务提交：去重进度 + 累计floor + 额度变化 + 结算结果 + 统计增量
  → 提交后确认spool进度，释放已处理原文
```

不得先保存完整业务明细、再依赖定时清理追赶全部输入。也不得把多次原始累计值直接相加。
批量合并发生在每个样本的权威判断之后：先求增量、逐样本舍入和限额，再累加已经确定的结果。
同一订阅的样本保持既有处理顺序，不能因并行/排序改变哪个样本获得剩余额度。

聚合可延迟明细展示，不得延迟必要的额度扣减而导致重复分配配额。
事务失败或结果未知不确认暂存；提交成功而确认丢失，重放只能识别重复，不再次扣量。
业务结果与去重事实不可分两次异步提交。无需新增强制Redis、Kafka或外部对象存储依赖。

## 3. 数据分层与默认保留提案

以下为建议默认值，不代表已修改现有配置。原先讨论的30天保留在此细化为30天小时历史，
分钟精度缩到24小时；长期结算结果与图表保留期独立。

| 数据 | 表示和作用 | 建议期限/数量 | 淘汰条件 |
| --- | --- | --- | --- |
| 当前节点状态 | 固定字段、每节点覆盖 | 跟随资产生命周期 | 删除资产；无逐事件历史 |
| 正常观察原文 | 默认不落历史库 | 无历史副本 | 提取状态并完成交付后释放 |
| 异常诊断样本 | 同节点/原因合并计数，正文限长 | 24小时，每节点最近20条 | 到期或超条数移除旧样本；未解决状态独立保存 |
| 未提交入账的暂存 | 可恢复批次、原始身份与样本 | 以是否提交为准，不能简单按天丢弃 | 原子入账且确认进度后释放；容量不足时向上游背压 |
| 分钟流量统计 | 聚合数值 | 24小时 | 对应小时结果已经核对；历史更老补报不重建分钟桶 |
| 小时流量统计 | 用户/订阅/必要服务维度 | 30天 | 日结果已经核对；不保留任意高基数字段 |
| 日流量统计 | 历史使用趋势 | 365天 | 超期只保留业务累计结果，不恢复过期图表桶 |
| 当前及必要结算结果 | 独立订阅权益代次、精确额度周期 | 按订单/订阅等业务生命周期 | 不能按图表TTL删除；历史结果折叠需符合业务读取与删除规则 |
| 报告去重与累计floor | 精确身份、序号区间、缺口/检查点 | 见第5节，独立于明细TTL | 仅有等价替代或终止准入证明后移除旧表示 |
| 已完成任务/运行日志 | 简短结果、独立错误诊断 | 成功7天、失败15天，审计30天（建议值） | 无活动引用且任务结束；未解决任务不靠错误日志维持状态 |

月趋势从保留的日统计生成，不为相同数据再默认添加一套永久月明细。
超过图表期限的合法新补报仍然入账并更新必要业务累计结果，不创建已经过期的图表桶再立刻清理。

正常、异常观察数据的存储上限只决定诊断保留，不能决定财务报告是否接收或节点统计是否持续更新。
旧观察原文当前沿用七天规则；缩短它必须在其与账务、当前状态彻底解耦且迁移核对完成后进行。
失败诊断超过期限可以移除正文，但尚未解决的业务状态不能随诊断一起消失。

## 4. 结算结果与查询模型

### 4.1 权威结果与展示统计分开

拟引入明确的计费主体和额度周期标识。计费主体绑定真实订阅/权益代次，不由当前用户信息反向补造旧归属。
额度周期保留准确的起止边界和操作代次，覆盖购买日重置、手动重置、套餐切换及倍率/计算规则变化。

权威结果保留原始上下行、已经确定的计费量和必要舍入/封顶证明，以及用于对账的样本计数。
当前额度、续费/重置核对从权威结果读取，不能从小时图表反推。
财务金额与流量额度是不同单位；流量统计不扩展成新的支付账务系统。

展示统计只保留页面实际查询需要的维度。用户总览、服务日统计可分别投影，
不把用户×节点×协议×倍率×发生分钟×接收分钟所有维度永久做笛卡尔组合。
统计口径明确区分发生时间与入账时间；发生很早但今天入账的数据不能错误地恢复旧周期额度。
图表日界使用明确的平台时区口径，保留必要版本信息；时区变化不重算财务结果。

### 4.2 合并与删除的事务边界

每个来源贡献只进入上一级一次，使用事务内的归并进度/代次识别，不能仅靠“目标已有该日期”推断完成。
冷却窗口内持续更新小时结果；小时折叠到日后，新的合法补报以增量更新日结果。
低层已过期不要求重新创建；保留期内需要修正时只能追加尚未投影的贡献。
不得每次扫描旧分钟行全量相加到日表，否则会重复累计。

所有用量、对账、分页、汇总及历史核算调用先迁移到新读取契约，才允许删除旧明细。
多层统计不得重复相加：每段时间明确由哪个层级覆盖；计费查询使用独立权威结果。
过期详情API返回“明细已过期，汇总仍保留”及可用粒度，不能把无明细展示成零用量或整页报错。

## 5. 补报身份与连接floor：两步实现，不能伪称已经有界

### 5.1 现有协议：先保持精确，压缩冷数据表示

旧随机report ID不能从最大序号倒推出是否处理过。当前MySQL字符串等价语义也不能随意换成
区分大小写的原字节摘要，否则会改变已有去重行为。

近期活跃身份/floor留在可更新的热表示；旧的稀疏身份、完成连接floor转成分组、排序的无损冷段。
可选编码为共享节点/运行代次、完整ID字典、整数差值/变长编码、固定版本二进制及整段压缩。
保留完整必要身份，不使用短哈希或有误判概率的过滤器作为唯一去重权威。
过滤器只能减少查询，命中后仍需精确确认。

冷段必须支持精确定位和受限解压。初始候选段大小256KiB–1MiB（未压缩），仅是待基准验证参数。
封闭段一次写；近期变更走小增量，之后归并，禁止每份报告重写大BLOB。
段目录、摘要、版本、逻辑条数、字节数和检索索引一同计入占用，不能只报压缩正文大小。
先使用现有数据库保存段和目录，无需管理员先配置新的长期存储服务。

冷热转换需先写入并读回验证，原子切换唯一生效表示，再删除原热行。
并发晚报与转换使用相同身份锁/代次；不能让两个表示各自入账。
损坏段报明确错误并保留已提交权威，不能把无法读取误判成“从未处理过”。

这一步降低每身份成本及索引开销，但仍随独立旧身份/连接数增长，不承诺固定总大小。
如果1000万条/小时同时意味着大量全新且永久可重放的随机连接，这一步单独不足以满足长期容量目标。

### 5.2 有证明的顺序/累计计费契约：减少身份数量

先核验现有节点上报是否已提供稳定的资产、运行代次、序号及必要的原始样本范围。
序号只能在同一明确作用域内比较；重启、序号重用、配置与权益切换必须可区分。

满足契约后，把已处理连续报告压为区间，未收到/未提交的缺口独立保留，不能只存MAX(sequence)。
已有语义压缩报告可能覆盖多个原始样本/序号；必须区分“包含的样本”与“尚未到达的缺口”，
不能凭first/last两端认定整个区间均已入账。不同ID但同序号、同身份冲突也需按已验证协议处理。
未知、待重试或被拒报告不得被伪装成成功入账范围。

仅压报告区间还不能移除每连接floor。要把增长从连接数降到计费主体数，
需要可验证的计费流累计契约：在订阅、权益、协议/倍率等真实计费边界内提供稳定累计状态和重放顺序，
使面板可以用每计费流的floor替代大量完成连接floor。
逐样本舍入、封顶、共享配额、配置变化和离线补报必须与现有算法逐项等价。
节点不能直接提交一个未经面板验证的“已扣量”数字代替核算。

现有上报信息若不足，必须先完善契约并做差分原型，不能直接在服务端删除连接floor。
能力协商不能成为旧节点接入的新增强制门槛：旧节点仍兼容精确旧模式，
但必须明确显示该模式的身份增长成本。未完成升级的报告源不享有“按主体增长”的容量承诺。
连续序号长期存在大量缺口时，区间也会碎片化；缺口压缩成本必须进入容量报表。

## 6. 历史迁移与物理空间回收

1. 固定一段历史上界和版本，登记旧行数、原始/计费总量、权益周期、舍入证明及去重语义基线。
2. 后台按主键小批次转换；启动不扫大表，不一次性复制全库，也不新增生产盘备份。
3. 建立新的结果及独立去重读取；旧来源ID到新结果的引用在迁移中保持可解析。
   不能让report receipt、待投影贡献或其他历史读取悬挂在已删除的ledger ID上。
4. 转换和并发新报告使用一致的进度边界，保证来源贡献不重复、不遗漏；支持中断和恢复。
5. 核对所有权威累计与查询后，分批淘汰原行，转为“新表示唯一生效”。
   无法核对的部分保留并计数，不能以校验失败为由永久阻塞其他无关段。
6. 先复用InnoDB内部空闲页，稳定逻辑增长。物理缩文件是独立维护操作，
   必须按实测临时空间和业务延迟安排，不能在接近满盘时盲目重建11GiB旧表。

新明细表可在去重/外键已解耦后评估时间分区淘汰；现有全局唯一键和引用约束不允许直接照搬分区DDL。
SQLite使用相同逻辑生命周期，不为了MySQL物理优化引入必须部署的新存储产品。
旧二进制不认识新结果/冷段时，不允许简单换旧镜像回退；兼容与转换回退必须有单独契约。

## 7. 容量预算替代单一64MiB闸门

64MiB不再作为“满后停止统计”的全局闸门。预算分成：固定当前状态、有限图表历史、
诊断样本、未提交暂存、必要财务结果/去重，以及数据库索引、redo/undo、binlog。
按实测每业务维度成本×活跃维度数×保留期预测容量；不能只限制某个payload列。

建议运行余量为max(2GiB,数据盘10%)，最终按并发维护峰值实测修订。
使用率85%开始预警和加快可选数据淘汰；90%停止可选诊断采样并降低非必要写入；
95%按剩余写入预算对新报告背压，保留源暂存，不确认尚未入账报告。
阈值是提案，不是现在修改生产配置；共享MySQL还需计入Connect、Xboard等其他应用占用。

低磁盘不能让全部回收任务直接退出。回收每批事务、解压字节、锁时长、最大运行时间独立受控，
避免清理本身制造大量binlog和写放大；失败可续跑，异常正文不得无限重复保存。
任何压力降级都不能随机丢财务报告或把暂存满理解为计费成功。

binlog单独列为运维策略；当前用户不需要恢复/复制，可另外规划关闭或短期保留。
关闭涉及共享MySQL及可能的重启窗口，不由ZBoard定时任务偷偷修改；本次仅记录方案，不执行。

后台只暴露清晰的保留设置、各类实际占用、增长速度和预计余量，不要求管理员理解每张内部表。
同时展示行数据、索引、表内可复用空间、物理文件和binlog，避免把逻辑删除说成磁盘已经释放。

## 8. 验收范围：数据正确入库与结果守恒

按用户最新要求，本轮采用可人工核对预期值的小样本，验证真实写入、读取和必要恢复路径。
不安排千万条/小时压测、两倍吞吐余量测试、长时间稳定运行或大规模容量认证。
后续如果实际负载需要，再单独安排性能验证；本轮通过不等于证明千万条/小时承载能力。

| 场景 | 验收结果 |
| --- | --- |
| 普通报告、同维度多次上报 | 增量、上下行和实际扣量写对，多次贡献合并到正确结果 |
| 多用户、多订阅、不同节点 | 归属正确、不串账，业务边界不被错误合并 |
| 重复、乱序和历史补报 | 应入账部分只计一次，历史补报可处理，旧统计不被错误覆盖 |
| 倍率、限额、重置和套餐切换 | 与既有逐样本预期逐项一致，不只比较原始流量总和 |
| 聚合与过期淘汰 | 用模拟时钟触发到期，明细删除后汇总与权威用量不变，超期图表桶不复活 |
| 旧数据转换、冷热压缩 | 转换/压缩后读回一致，重复执行不重复汇总，旧身份仍可精确去重 |
| 提交失败、提交后ACK失败及恢复 | 不假确认、不丢量、不重扣；必要并发转换没有双重入账 |

SQLite及真实MySQL按改动范围执行小样本验证，不在生产跑压力测试。
每个用例记录输入、预期结果、实际数据库读回和必要行数；验证“写对且读对”。
压缩只需对同一小样本核对解压一致、目录/索引可查询，记录实际前后字节数，
不预设压缩倍数，也不要求吞吐、延迟、全库分配或binlog写入量达到特定性能指标。
完成后给出简短验收结果和未覆盖范围，不用长时间运行代替正确性证据。

## 9. 实施工作包与完成标准

- **P0 契约与基线**：枚举全部账本/去重/额度/展示调用、身份等价语义和上报能力。
  建立覆盖不同倍率、旧补报、重置的小样本预期与差分验证。完成前不删财务行。
- **P1 观察链路止增**：复用已提交0085，另行取得构建部署指令后上线，量测观察两表及binlog增量。
  观察收敛不代表P2–P4已完成。
- **P2 结果权威与有限历史**：完整实现结果写入、所有读取迁移、晚报增量修正、分层淘汰及受控历史转换。
  SQLite与真实MySQL核对后，才允许清除已被证明替代的账本明细。
- **P3 冷身份精确压缩**：实现有界冷段、索引、冷热事务、损坏恢复与旧身份迁移；
  单独证明其空间成本，不把它宣传成解决所有新连接线性增长。
- **P4 计费流和序号契约**：先验证现有能力，必要时协调上报端演进；完整调用方迁移和兼容测试。
  逐样本算法等价、必要序号/累计契约成立且小样本新连接与补报验证通过后，
