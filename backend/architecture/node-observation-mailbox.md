# 节点观察状态与账务依据分离（0085）

## 问题与边界

旧的64MiB上限仅控制可选原文parts，不包含事件头、回收凭据、索引或binlog。
容量耗尽后每个新事件仍生成header和capacity_exceeded凭据，却不会进入观察worker，
形成“统计不更新、辅助表继续增长”。2026-11-12的生产检查已验证这条路径。

本轮替换新事件的观察写入，不调整财务身份、逐样本舍入、限额、重置周期或历史补报准入。
生产发布前后仍需分别测量物理分配、每表逻辑增长、binlog增量和磁盘余量；
这不是全库固定空间或上线效果已验收的声明。

## 新写入与投影

- `node_observation_mailboxes`以NodeID为唯一主键，一个节点只占一行，删除节点由FK级联移除。
  资产标签随行保存，编号复用不能采用旧资产状态；同编号的新标签覆盖原行，不按runtime新增行。
- 一个财务批次先按节点合并，再各写一次。独立保留最新活动位置Latest和最新统计位置Stats，
  不把flow更新伪装成统计。只保留位置、原接收时间和三个计数，不持久化payload、principal或flow原文。
- JSON最多4096字节；过长、不可直接表示或转义后过大的辅助标识以SHA256收敛，
  同一转换用于旧来源比较。此摘要只用于观察比较，绝不替代财务身份或权限依据。
- producer在已有财务锁之后获取节点SHARE NOWAIT，再锁mailbox；忙节点立即返回并重放原spool，
  不跨订阅锁等待节点管理锁。数据库写入失败整体回滚；观察内容冲突不会阻断已合法的计费。
- worker先锁节点UPDATE SKIP LOCKED，再mailbox，再资产状态，同一事务写计数、保存来源并ACK。
  同节点多worker最多完成一次；忙节点不阻塞同轮其他候选。ACK后保留同一行，之后覆盖。
  pending_since保留本轮首次排队时间，覆盖新数据不重置队龄；按该时间及节点编号的索引取候选，
  避免持续上报的小编号节点反复抢在老候选前面。
- 已应用Latest/Stats的有界原始位置内联在`node_observation_states`，各不超过4096字节。
  这使当前来源不再依赖逐事件原文。引用字段继续提供不透明关联号，不声称新关联号都有可重放原文。
- 继续遵守原资产隔离、runtime顺序、历史位置拒绝回退、心跳接收时间覆盖和纳秒时间栅栏。
  source/runtime不一致仍明确unknown，不用应用时间替代接收时间。
- 同位置统计冲突保留已证明数值，固定reason单独暴露；有更新统计后恢复。
  损坏mailbox停止重复执行并标记，下一次合法上报可覆盖恢复，仍需经过已应用位置比较。

当前观察正文随节点数增长，与报告数量无关；一节点mailbox及两份内联正文上限合计12KiB，
不包含行、索引、旧资产墓碑及保留的历史兼容材料。覆盖写入仍有正常redo/binlog成本，
不宣称这部分写入量为零。后台容量观测同时读取新mailbox的待处理状态。

## 旧材料生命周期

旧pending/claimed/held来源继续使用原锁、租约、完整性检查和容量规则。
当前Latest/Stats/Floor引用、活动租约及不一致材料仍受保护。
原文保留仍沿用旧七天规则，本轮不把未核对原文提前丢弃。

新增固定一行的GC主键游标，每轮最多检查200个header，各源单独短事务。
源产生满24小时，且原文回收已确认complete、remaining_bytes=0、header摘要匹配、
无任何当前引用、无活动租约且无残存part，才可原子删除header及receipt。
Applied-unreferenced来源还必须有原文验证标记。失败回滚两行删除；损坏证据留存。
主键扫描一轮结束休眠一小时，跳过的忙节点或仍被引用的记录下一轮复查。
没有启动时历史全表扫描、重建大表或额外备份。旧回放API仍只处理其真实存在的旧来源。

清除这些辅助身份不会影响历史补报：财务report receipts、累计floor/checkpoint、
spool提交以及账本均不在该GC事务中。重放不会再补造逐事件观察凭据。

## 明细与xboard对照

对照本机`/Volumes/tool/dev/Xboard`的`3f81948762204d7146acdf0e3facfb5a199d8280`，
阅读BatchTrafficFetchJob、TrafficFetchJob及ServerService.log。
其方式偏向累计u/d、异步增量入账和同维度日志合并，值得借鉴的是减少重复明细表示。
ServerService的日期窗口代码没有在本轮运行验证，不能把它当成完整的小时统计正确性证明。
也没有从这些增量代码中得到“无限期旧报告重放仍精确去重”的保证，因此不照搬其账务算法。
对照仓库已有的Dockerfile、SingBox.php改动未触碰。

ZBoard新账本已是`settlement.minute`：按用户、订阅、权益代次、节点、协议、倍率、
事件分钟和接收分钟等维度合并，累加已经逐样本计算的扣量，不在聚合后重算舍入。
已完成连接的完整行按现有24小时策略转移到紧凑累计检查点；会话诊断原文与边界点24小时，
分钟连接图十五天，主机监控1440个分钟槽，其他分钟指标与任务有各自保留策略。
详见[存储增长与保留策略](storage-growth-and-retention.md)。

历史逐报告账本仍占空间，不能因已有分钟汇总就直接删除所有旧身份或重算历史金额。
无限历史补报加精确去重必然需要保留某种身份信息；当前设计减少重复正文与索引，
不承诺所有账务表恒定大小。本轮没有进一步改写既有历史账本或增加备份。

## 迁移、复制与回滚

0085只扩展小型观察状态表并创建新表，不回填数百万事件，不阻塞启动做历史清理。
SQLite/MySQL均验证PK、非空字段、TEXT、待处理复合索引、正文长度CHECK和节点级联约束。
MySQL允许其对OCTET_LENGTH规范化后的等价LENGTH约束。已记账的迁移缺约束或缺字段拒绝启动，
未记账的中断DDL可续跑。独立worker准备检查也要求0085及真实表约束。
复制清单包含mailbox、内联来源和GC游标；复制后可从pending继续，源库不被确认。

旧writer/consumer必须在切换时静默。旧二进制不认识新mailbox，不能与新观察worker混跑，
也不能把旧header队列当成新的完整事件审计。down迁移明确拒绝删除状态；
回退需单独核对版本兼容性及未应用mailbox，不能仅删0085记录。
