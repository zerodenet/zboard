# 计量统计性能与数据完整性

2026-10-16。范围限 ZBoard；统计要求数秒内可见。以下区分本轮已实现改动与后续方案，不代表生产容量或线上缺口已验收。

## 已核实的现状

| 路径 | 当前成本或限制 | 本轮处理 |
| --- | --- | --- |
| `meteringstore.UsageSummary` | 原先每次分别扫描全部明细、当天明细计算用量 | 同一读事务内一次扫描小时汇总，同时计算总量与当天用量 |
| 维度统计缺口 | 管理页缺少统一的用户/节点/订阅/协议端点汇总与下钻入口 | 新增 `view=breakdown`，统一提供上下行、原始/计费流量、区间总量、稳定排行分页与对象名称 |
| 管理页首次加载 | 进入页面即请求聚合明细、全区间统计、对账与图表 | 默认进入统计概览；明细与对账显式打开后才读取，维度汇总在可见页面每三秒刷新 |
| `meteringstore.Records` | 分页前分别扫描统计和总条数 | 合并为一次统计扫描；页面继续按游标读取权威明细 |
| `meteringstore.TrafficTrends` | 半小时/四分之一小时时区原先回退全区间明细 | 各日使用完整小时汇总，仅读取日边界的不完整小时明细 |
| 非 UTC 日趋势 | SQLite 小时 TEXT 键与 `time.Time` 绑定格式不同，日边界小时可能被分到 NULL 日期 | 整小时源按统一时间键比较，补齐边界回归 |
| `AddProtocolEndpointUsage` | 批内虽合并端点/日期，但每个汇总项仍独立执行 UPSERT | 按键排序，每批至多 100 项执行原子增量 UPSERT，保留最后事件时间和事务回滚 |
| 聚合明细 `Usage` | 页面及部分统计仍读取明细；SQLite 有受容量约束的增量缓存，MySQL 无同等机制 | 本轮未重写分组 ID、游标或去重语义 |
| 对账 `Reconciliation` | 需要独立对照账本，站点级核对仍可能遍历全部账本 | 保留独立核对依据；不能换成与余额同源的缓存冒充对账 |

`traffic_usage_hourly` 已经随计量事务更新，包含当前未结束的小时；“小时粒度”不等于“一小时后才更新”。现有展示快照有效期为两秒，入账与授权不使用该缓存。本轮没有增加写入表、后台汇总队列、外部数据库或缓存服务。

## 完整性边界

用户本轮所说的“统计缺口”已明确为业务维度不足，本轮补齐上述四种维度。以下采集完整性问题另外核对，不能与维度缺失混为一谈：

1. **事件接收/消费延迟**：使用已有 spool checkpoint、消费耗时、接收至提交延迟；积压并不等于未收到数据。
2. **事件序列覆盖不完整**：现有 coverage 能报告序列缺口、首次采集预热、事件流过期。不能把缺口自动解释成零流量。
3. **总量与时间分布不同**：运行代次/Flow 的累计计数可以补回后续增量，但增量按报告事件时间入账；批内合并、延迟上报和缺失中间采样无法精确还原每一分钟的真实分布。不能平均摊平后声称准确。
4. **查询本身丢分组**：本轮 SQLite 日期键问题已通过构造边界数据复现并修复；这不证明所有线上缺口都来自它。
5. **缺少业务维度或指标**：需要明确用户、订阅、节点、协议端点、上下行、扣费倍率、在线连接数等指标的口径。在线连接数来自存量快照与生命周期事件，不能拿流量记录条数代替。

维度下钻不会把用户/订阅整体的连接峰值套用到某个节点或协议端点：缺少对应细分投影时返回未知，避免展示范围不匹配的数字。

余额、流量计费、配额耗尽、去重游标、发布意图仍保持原有事务。汇总字段不能替代原始累计计数进行计费。

## 下一阶段设计

这些项目尚未实施；具体容量和保留期应依据实际事件速率、存量、查询分布及回放窗口确定。

### 1. 让常用统计彻底脱离明细扫描

- 新维度接口已复用统一汇总源；继续迁移剩余依赖明细的统计查询，保持上下行和计费流量口径一致。
- 为确实需要的分钟趋势增加有界粒度读模型；历史周期降采样到小时/日。桶内持续增量更新，不能等桶结束才发布。
- 热路径按批次合并相同键，事务提交后即可查询；不保存与原始流量事件等量的统计副本。
- 聚合记录使用稳定的复合桶键，避免依赖某条明细的 `MIN(id)`；迁移聚合接口时保留原始明细游标契约，并核对现有调用方。
- 分页明细保持按需查询。全量对账、复杂跨维去重、导出作为独立有界任务，避免默认页面不断触发全账本聚合。
- 所有统计响应明确更新时间及覆盖状态；缓存时间与消费延迟分别展示，不把“有缓存”当成“数据完整”。

### 2. 控制数据量之前，先解除账本、去重和统计的耦合

当前 `(node_id, report_id)` 去重直接查 `TrafficRecord`；SQLite 的小时投影还会在删除账本行时同步扣减。直接按天删除明细会同时破坏回放幂等、历史汇总与对账基础。

后续压缩/归档必须满足：

- 已提交用量与扣费事实可追溯；结算事实和展示采样分开定义。
- 独立持久化所需去重身份、运行代次、累计游标及结算边界；归档后的重复投递不能再次扣费。
- 日/月汇总不能随明细归档被扣掉；先完成读模型维护与数据库迁移/导入/回滚语义，再启用保留策略。
- 只对已确认且越过回放边界的数据分批压缩，保存任务水位、校验值和失败记录，可中断继续。
- 迟到事件写回其事件时间的统计桶，不能为缩短存储而丢弃待处理事件或改写历史。
- 通过配置明确详细诊断记录与长期结算事实的保留策略；本轮不修改默认值或清除历史。

### 3. 压测与上线门槛

- 容量测量至少覆盖：事件/秒、活跃 Flow 数、每批 SQL 数、数据库写延迟、读 p95、消费水位、DB/WAL/索引增长、进程 RSS。
- 单独测试正常流量、迟到/乱序、重复投递、重启后回放、跨日/时区/夏令时，以及数据库慢写/取消/回滚。
- 分别报告统计 SQL 耗时、HTTP 端到端延迟和可持续入账吞吐；SQL 微基准不能代表线上容量。
- 实际 MySQL 事务测试需要 `ZBOARD_TEST_MYSQL_DSN`，由现有 CI MySQL job 执行；本机未配置时跳过，不以 SQL DryRun 代替真实数据库验收。
- 上述改造均通过 ZBoard 的计量与统计能力完成，不涉及节点启动、停止、重载或修改内核行为。

## Connector 信息收敛（2026-10-16）

此次处理仍全部位于 ZBoard，不修改 Zero、订阅配置或在线节点。保留当前八类事件订阅：累计流量用于入账、完成事件用于最终结算、生命周期用于连接数与 Fair Use、节点统计与引擎事件用于状态。不能只保留最终完成事件，否则长连接用量与配额判断会滞后到连接结束。

新增处理：

- 接收 `flow.updated` 时只保留 Flow/Principal 身份、运行代次、修订、累计上下行、事件/接收时间和序列；Principal 按嵌套 auth 的实际解析结果保存。`stats.sampled` 仅保留三个已消费计数器。诊断/目标地址等未消费字段不再复制到面板缓冲文件；不删除已有待消费记录。`engine.warning`/`config.changed` 目前只消费存在性与覆盖元数据，也进入轻量缓冲，避免告警洪流同步写库。
- 默认空闲消费间隔从五秒调整为一秒；有积压时继续调度，轮次达到 200ms 软预算后在窗口边界让出任务执行器；当前有界窗口会先完成，该预算不代表硬性响应时限。消费预读最多 2,000 条、序列化记录预算 8 MiB；允许最后一条跨越预算，以保证历史大记录能继续消费。旧记录最大尺寸和压缩块解码上限仍适用，因此 8 MiB 不是进程 RSS 上限。
- 一个预读窗口内，按节点/内核代次/Flow 合并同一分钟内的单调累计快照；Principal、来源、配置/Flow 修订、分钟变化，以及无可靠代次/序列、序列重复、计数回退时保留边界。重复 report ID 不参与合并；已存在且尚未由对应累计游标覆盖的报告、MySQL 排序规则等价的报告，回退逐报告短事务处理。每个被合并报告的累计计数保留为有界内存检查点，供计量事务逐次计算倍率取整，而非一次乘以合并后的流量。账本附带样本数、首尾序列与取整分子之和，可验证 `额度截断前费用 = (raw_bytes * multiplier_milli + rounding_numerator) / 1000`；实际费用仍受剩余额度约束。
- 聚合后的结算事实仍写入原有账本、小时/端点投影和累计游标。SQLite 每个权威事务最多 32 个流量样本，MySQL 最多 128 个；节点观察与对应结算事务一起提交。覆盖率仍使用全部原始事件的序列，按节点批量写入，不把正常消费合并当成缺口。
- 整窗权威投影完成之后才确认 spool checkpoint。中途事务/检查点失败后保留整窗；已提交部分由持久化累计游标和报告去重保护。覆盖率仍是辅助、失败开放的投影，不阻塞结算。
- 压力语义压缩不再丢弃累计计数不同的中间报告；仅允许同一身份、配置和分钟内 payload 相同的 Flow 快照相互覆盖。避免进入消费窗口前丢失倍率取整依据。压力压缩后的序列缺失仍不冒充完整覆盖。
- 运行诊断新增已投影 Flow 样本数与合并更新数，与原有处理数、积压、耗时和延迟一起观察。

边界：这减少了面板缓冲字节数、重复快照形成的 SQL/账本行和节点观察写入，不减少 Connector 已发出的 HTTP 请求数，不删除历史账本，也不省略短连接的开始/完成事件。连接数/Fair Use 的生命周期存储还需单独评估，不能宣称任意流量模型都减少相同比例。分钟内合并后的增量按最后快照时间写入，不声称恢复逐秒历史分布。

回归增加累计快照洪流、分数倍率逐报告取整、配额截断、检查点/分段事务失败回放、代次/身份/分钟边界、计数回退、大整数、完整序列覆盖和大 payload 的原始/压缩缓冲读取。MySQL 实库测试依赖现有 CI 数据库环境，本机缺少 DSN 时明确跳过。`BenchmarkZeroEventReduction` 比较相同的 32 个活跃 Flow、1,024 个累计报告在小窗口和预读合并后的 SQL/处理成本；不包含 HTTP、spool 写入与 fsync，不等于生产吞吐。

本机合成基准（3 次/模式，SQLite，非生产容量）：相同 1,024 个输入报告，小窗口为 2,432 SQL、约 1.116 秒/轮；预读合并为 82 SQL、约 0.097 秒/轮。不同活跃 Flow 比例、倍率、报告回放、数据库竞争和硬件会改变收益，不能外推为线上接收能力。

本轮验证：后端 `GOMAXPROCS=2 go test -p 2 ./...` 全量通过；最终取整凭据与消费调度调整后，相关专项再次通过。相关包 `go vet`、本地 `cmd/zboard` 构建、OpenAPI 校验和 `git diff --check` 通过。OpenAPI 保留 282 条已有警告；MySQL 实库用例因未配置 DSN 跳过。未提交、发布、部署或操作节点。


## 账户概览剩余流量慢读（2026-10-16）

概览原先请求完整 `traffic/summary`，需要同时返回历史累计、今日用量和剩余额度。即使订阅列表已经返回，额度卡片仍会等待历史聚合与统计连接池。此前把账本查询改为小时汇总减轻了历史扫描，但没有解除这个依赖。

增加原接口的 `view=quota` 读取模式：只从当前有效、未到期且仍有余量的全部订阅聚合额度，使用账户权威读取连接，不进入历史统计连接池，不缓存余额。自助接口强制当前用户，管理员入口仍逐次核验权限；原完整统计接口继续提供历史用量。概览仅调用此模式，取消该卡片中的累计历史用量，不使用最近三条订阅或前端相加推算总额。刷新时继续展示上次成功值，刷新失败明确标注。

回归覆盖超过三条订阅的完整合计、到期/失效/耗尽排除、自助范围、管理员撤权、实时余额变化、取消、历史连接池被占满时额度独立返回，以及前端慢刷新保留已确认数值。代码层依赖已验证；未取得线上请求耗时/数据库执行计划，不能将它描述为已确认的线上唯一瓶颈或已部署恢复。

额度快路径验证：后端额度/完整统计专项、架构与 API 测试通过；前端账户概览、API 和资源生命周期三组共 26 项测试通过。类型检查、生产构建、相关包 go vet、OpenAPI 校验和 git diff --check 通过。MySQL 实库用例本机未执行；未提交、发布或部署。

## 平台落地范围与交付顺序（计划，首批状态见末节）

针对慢读、加载阻塞和事件洪流，平台治理覆盖采集、业务状态、统计投影、页面读取与运行诊断；业务所有权继续留在现有 capabilities / application / persistence 中。此节保留完整交付计划，首批完成项及未关闭边界见末节，不代表下列能力已全部实现，也不引入通用查询引擎或新的权限体系。

以上为抽样核实的结构性风险，不是线上慢查询排名，也不代表已完成全平台逐入口审计。

### 统一读取约定

| 类别 | 数据来源和一致性 | 页面约定 |
| --- | --- | --- |
| 当前业务状态 | 余额、额度、订单状态、权限及当前配置读取权威状态；提交操作时再次核验 | 首要信息独立返回，不能等待排行榜、全历史统计、外部探测或远端执行 |
| 展示统计 | 由领域维护增量汇总；允许数秒展示延迟，展示更新时间、来源水位和覆盖情况 | 可见区按需刷新；刷新不重叠，同一主体/权限范围/筛选条件可合并重复请求 |
| 列表与详情 | 有界分页，只取列表字段；准确总数、跨页统计和详情根据用途单独读取 | 首次打开可浏览第一页，搜索只缩小范围；需要准确总数时明确请求，不用当前页推算总量 |
| 重计算与外部执行 | 全量对账、导出、重建、远端执行进入现有持久化任务体系，有进度、执行水位和重试语义 | 操作受理与执行完成分开；超时保留未知结果与核查入口，不能靠刷新或重复执行冒充恢复 |

接口应按同一用途组织，不要求“一张卡片一个接口”。也不禁止 `Promise.all`；要防止关键结果在服务端或渲染条件上依赖无关的慢结果。

当前状态优先读取已经存在且规模受控的业务状态，不要求所有全站总数都同步扫业务表。随规模增长的统计总数由所属领域维护可核对的汇总。

### 建议验收目标

以下是待在参考环境验证的目标，不是现有性能承诺：

- 关键状态接口服务端 p95 不超过 300ms；普通分页列表 p95 不超过 800ms。统计读取受预算约束，超预算进入任务或清楚返回暂时不可用。
- 数秒统计按完整链路计时：从 ZBoard 收到事件到可见页面展示，p95 目标不超过 5 秒。分别记录入账/投影、缓存年龄、请求与刷新等待，不能只看某个一秒定时器；上游尚未送达的时间另计。
- 对比小数据和增长数据：关键状态读取不依赖历史流量规模，普通首屏不装载全量详情或先完成全站统计。
- 在持续事件输入、慢 SQL、统计池占满和后台重建并存的负载下，交互仍满足目标，计费和权限校验仍准确，积压和过期状态可见。
- 重复/乱序/迟到、额度耗尽、退款修正、取消、重启回放和归档后重放都必须通过。面板重启验收同时核对客户端已有连接，不以“节点重新在线”代替连接未中断。
- 每项按“代码完成、自动测试、本地容量、CI 实库、发布、线上验收”分别记录状态。当前本地修复尚未发布，不能据此声称线上已经达标。

缓存仅用于允许滞后的展示读取，必须限定主体/权限/筛选范围、容量和年龄。计费、配额判断、订单确认、权限准入继续依据权威事务；不能以展示缓存作为依据。插件宿主侧的读取和任务同样遵循资源与状态约定，插件业务仍归其所有者，不在 ZBoard 增加特定渠道分支。

### 管理概览按用途拆分

原 `/admin/dashboard/overview` 不带 `view` 的完整响应保持兼容。新页面使用三个独立视图：

| 视图 | 数据来源与成本 | 页面行为 |
| --- | --- | --- |
| `current` | 权威连接；两条只读查询，订阅健康 + 当前运行/基础设施/待办；不读取订单、流量历史或趋势，不调用统计连接工厂 | 当前状态独立显示与重试；请求内查询预算 3 秒，客户端 5 秒；前台 3 秒刷新 |
| `statistics` | 报表连接；三条查询，选定/上一周期订单、该区间新增订阅、用户及计费流量投影 | 独立显示与重试；请求内查询预算 8 秒，客户端 10 秒；前台 3 秒刷新 |
| `trend` | 报表连接；一条订单时间桶查询；保留原时区、金额/币种、退款和比较口径 | 独立显示与重试；8/10 秒预算；15 秒刷新 |

当前状态卡片前移至首屏；本期计费流量归经营统计区域，避免慢统计形成空卡片或延后当前状态。趋势独立返回币种/混合币种元数据，并按其自身数据计算图中合计，不借用另一读取的币种或合计；不同时间桶或同一时间桶多币种时均转为订单量。

排行与事件仍按各自请求读取，每 15 秒刷新。切换经营周期只重置统计/趋势；节点/用户排行切换只影响对应排行。当前服务状态不受周期切换影响。后台页面不发起定时读取；卸载取消未完成请求；每个区域最多连续三次自动失败，之后需手动重试，成功后恢复自动读取。

`as_of` 是读取开始时间；统一前端状态的 `lastSuccessAt` 是收到成功结果的时间，两者均不是事件已全部入账的水位。积压、处理延迟和缺口仍通过已有运行诊断判断，不能由“页面请求成功”推断采集完整。

查询拆分是解除等待关系，不是减少所有 SQL：当前/统计/趋势分别为 2/3/1 次查询，旧完整视图仍为 4 次。订阅当前状态和未恢复发布仍有聚合成本；后续增量投影须在真实数据规模下验证。SQLite WAL 独立读池可验证历史池被占满时当前状态仍返回；MySQL/内存库/非 WAL 若共用池，仍可能争用同一池或 CPU/IO，本批不宣称物理资源隔离。

### 统一读取生命周期

`useRemoteResource` 提供 idle/loading/ready/refreshing/stale/error/unauthorized/forbidden，以及失败类型、上次成功时间、连续失败数和自动刷新准入。保留模块自己的数据与筛选，不建立全局业务数据仓库。

`useRemoteTable` 与 `useCursorTable` 均复用同一读取实现；原有行、准确总数、聚合、筛选面、分页修正、游标和可写引用接口保留。表格刷新失败保留上次结果；401/403 清除该资源结果。分页修正在同一个可取消、默认 30 秒的读取内进行，最多修正三次；旧作用域不得执行列表提交回调。成功空列表与尚未读到数据通过 loaded/phase 区分。重置/换主体由模块调用 reset，取消代次阻止晚返回覆盖。

管理概览、账户额度、后台任务页已使用共同状态展示。运行状态、任务名录、队列明细独立读取；队列不再等待运行诊断成功才请求或显示。其余已有表格通过共同实现继承取消、超时、鉴权失败清理和过期状态；各页面专有文案/权限上下文仍由页面维护，并非全部模板已重写。

### 耗时诊断

在现有安全 HTTP 日志上补充 `Server-Timing`：`app_headers` 为开始处理至首次最终响应头的时间；`sql` 为 GORM 语句累计耗时，包含语句连接获取和执行/读取；`admin_auth`、`dashboard_current/statistics/trend/full`、`dashboard_rankings`、`usage_quota` 为代码固定阶段。HTTP 日志保留完整请求持续时间与完成时的阶段数据。已有任务接口的分段计时头继续保留。

计时器按请求分配，最多 16 个固定名称；不建立无限增长的进程内样本表，不收集查询参数、SQL 文本/参数、请求头/体或用户标签。查询日志包装不额外求值 SQL 回调，沿用原日志级别。没有缓冲响应体；流式 Flush、Hijack、Push、Unwrap 和已有 Server-Timing 得以保留。

`sql` 不是“纯执行时间”，也不等于精确的本请求排队耗时；并行 SQL 的累计值可高于墙钟时间。运行诊断的 `accounting_db/traffic_read_db.wait_count/wait_seconds` 仍为全池累计值。诊断顺序：先按路由看 HTTP/阶段耗时，再对照 SQL 和池等待趋势，最后核对 event_consumer/spool 的积压和接收至提交延迟。仍需在实际数据库取得执行计划与负载数据，不能仅凭两次池快照差值给某个请求分摊等待时间或宣称 p95 已达标。
